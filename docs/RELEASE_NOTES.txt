# v.1.2.0
- Results ya no depende de Kitpymes.Core.Shared ni del framework de ASP.NET Core (Microsoft.AspNetCore.App). Sólo necesita .NET 10. Motivo: el dominio usa Results (también a través de Kitpymes.Core.Mediator.Abstractions) y no puede depender de ASP.NET Core.
- Lo que se usaba de Shared es ahora interno, con los mismos textos y el mismo comportamiento que la 1.1.1: títulos "El proceso se ejecuto correctamente" y "Se produjeron uno o más errores de validación" (en inglés con la cultura en; cualquier otra cultura, en español), TraceId secuencial, mensajes en blanco ignorados y mensajes unidos con ", ".
- CAMBIO DE COMPORTAMIENTO (la API pública no cambia, pero un catch puede dejar de funcionar): ApiResult.Error(...) sin ningún mensaje ni error, y ResultOptionsError.WithErrors(tuplas) con un campo o un mensaje nulo, vacío o sólo espacios, lanzan ArgumentException en lugar de SharedException. El mensaje no cambia. Un catch (SharedException) alrededor de estas llamadas deja de capturarlo y la excepción sigue subiendo: hay que cambiarlo a catch (ArgumentException). Son errores de programación: lo mejor es no capturarlos.
- Cambio para quien compila contra Results: quien usaba Shared o ASP.NET Core sólo porque llegaban a través de Results tiene que referenciarlos él mismo (PackageReference Kitpymes.Core.Shared o FrameworkReference Microsoft.AspNetCore.App, o el SDK Microsoft.NET.Sdk.Web).
- Sin cambios en la API pública: el empaquetado valida la API contra la 1.1.1. El paquete no lleva frameworkReferences ni la dependencia de Shared (lo comprueba la pipeline) y sigue llevando el analizador KPY0003.
- Sin cambiar (como en la 1.1.1): WithErrors(tuplas) con un campo repetido y otro mensaje se queda sólo con el último mensaje.

# v.1.1.1
- Corregido: ResultOptionsError.WithErrors (ResultSettingsError.AddErrors) sustituía los errores de llamadas anteriores en lugar de sumarlos. Venía de la 1.0.1. Ahora:
  - junta los errores de cada llamada y, si un campo se repite, une sus mensajes en orden y sin repetidos (como ya hacían los mensajes);
  - guarda una copia: los cambios posteriores en el diccionario de quien llama ya no se reflejan; se respeta su comparador de claves si es un Dictionary;
  - un campo con la lista de mensajes a null cuenta como vacío.
- Interno: Result.FailureFor crea el fallo igual para Result y Result<T> (sin cambio de comportamiento).
- Tests de mutación con Stryker.NET en cada rama: Results pasa del 84,13 % (medido sobre la 1.1.0) al 94,12 %, y el analizador del 71,88 % al 81,25 %. Casos nuevos en los límites de los códigos de error.
- Sin cambios en la API pública. El empaquetado tiene activada la validación de paquete contra la 1.1.0.

# v.1.1.0
- Nuevo: Result y Result<T> para dominio y aplicación, sin nada de HTTP. Los errores de negocio se devuelven en el resultado.
- Nuevo: Error con Code (forma <Modulo>.<Motivo>, comprobada al crearlo), Message, Type (Validation, NotFound, Conflict, Unauthorized, Forbidden, NotContracted, Unexpected) y errores por campo (FieldError: campo, código con la misma forma y mensaje).
- Nuevo: conversión implícita de Error a Result y a Result<T>. No hay conversión implícita desde el valor; se usa Result.Success(valor).
- Nuevo: Result<T>.TryGetValue(out value). Result.Success(null) lanza ArgumentNullException: un éxito siempre lleva valor.
- Nuevo: Result.FailureFor<TResult>(error) crea el fallo de un tipo genérico (pensado para el mediador).
- Nuevo: result.ToApiResult() traduce a ApiResult (400, 404, 409, 401, 403, 403, 500) y nunca copia excepciones. ErrorType.ToStatusCode() da el código HTTP.
- Nuevo: ApiResult e IApiResultError tienen Code y FieldErrors; ResultOptionsError.WithCode/WithFieldErrors y ResultSettingsError.Code/FieldErrors para rellenarlos. En la interfaz tienen implementación por defecto (null): las implementaciones propias siguen compilando. Las respuestas JSON llevan estos dos campos nuevos (a null si no se rellenan): ojo con clientes que validen el esquema de forma estricta.
- Nuevo: analizador KPY0003 dentro del paquete. Da error si se tira un Result sin mirarlo (también tras await o si es un Task<Result> sin esperar); '_ =' es el descarte explícito. Se puede bajar en .editorconfig.
- Aviso: los nombres nuevos Result y Error pueden chocar (CS0104) con otras librerías de resultados importadas en el mismo fichero; se resuelve con un alias de using.
- Sin cambios que rompan la 1.0.1. El empaquetado valida la API contra la 1.0.1 (EnablePackageValidation).
